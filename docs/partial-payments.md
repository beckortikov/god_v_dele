# Частичные оплаты и графики платежей

Участник может платить за месяц частями: $300, потом $200, потом $500. Каждое поступление хранится отдельно, а месяц показывает, сколько оплачено и сколько осталось.

## Что изменилось

### Данные

| Таблица | Что в ней | Сколько строк |
|---|---|---|
| `monthly_payments` | **График**: месяц участника с планом (`plan_amount`), итогом оплат (`fact_amount`) и статусом | одна на участника и месяц, как и раньше |
| `payment_transactions` (новая, миграция 014) | **Поступления**: сумма в $ и в валюте, курс, дата, счёт, комментарий, кто внёс | сколько угодно на месяц |

Итог месяца пересчитывает триггер в базе после каждого добавления, изменения или удаления поступления:

- `fact_amount` — сумма поступлений в долларах;
- `status` — `paid`, если оплачено не меньше плана (сравнение в центах), `partial`, если что-то оплачено, `pending`, если ничего;
- `paid_date` — дата последнего поступления;
- валюта, курс и счёт берутся из последнего поступления; `original_amount` — сумма в валюте, если все поступления месяца в одной валюте.

Поэтому план-факт, аналитика, просрочки, уведомления и поиск, которые читают `monthly_payments`, работают без изменений и видят частичные оплаты.

### Пока миграция 014 не применена

Приложение работает **точно как раньше**: одна оплата на месяц, повторная оплата заменяет первую (с предупреждением в форме), отчёты считаются по `monthly_payments`. Приложение проверяет наличие таблицы само и замечает миграцию в течение минуты, перезапуск не нужен.

Работает в обоих режимах:

- форма «Новое поступление» показывает «Оплачено $X из $Y · осталось $Z» за выбранный месяц;
- карточка участника показывает весь график: все месяцы от даты начала на срок программы, включая месяцы без записи («Нет оплаты»), со статусами «Просрочено», «Частично», «Оплачено», «Текущий», «Будущий»;
- «Сформировать график» (в карточке и массово на странице «Участники»), правка плана месяца, кнопка «Внести оплату» у месяца.

### После применения миграции 014

| Где | Что меняется |
|---|---|
| Форма «Новое поступление» | Сумма заполняется остатком месяца, сохранение **добавляет** поступление, предупреждения о замене нет. Под суммой видны поступления месяца. |
| Доходы и расходы → Поступления | Одна строка на каждое поступление, с подписью «за сен 2026» и статусом месяца («Месяц оплачен» / «Частично»). Удаление убирает одно поступление, месяц пересчитывается. |
| Импорт поступлений | Каждая строка файла добавляет поступление; переключателя «Заменять существующие оплаты» больше нет. Дубликатом считается та же дата, участник, валюта и сумма. |
| Карточка участника | Месяц раскрывается: даты, суммы, счёт, комментарий каждого поступления, удаление. |
| Мои оплаты (кабинет участника) | Под каждым месяцем список поступлений. |
| Остатки счетов | Считаются по поступлениям: каждое на свой счёт (для счёта в сомони берётся сумма в валюте, как раньше). |
| ОПиУ и Главная | Денежные показатели (поступления месяца, остатки, с начала года, график доходов, «последние платежи») считаются по датам поступлений, поэтому месяц, оплаченный двумя частями в сентябре и октябре, попадает в оба месяца. Плановые показатели — по графику. |
| `POST /api/monthly-payments` (старые клиенты) | Больше не перезаписывает месяц: создаёт его при необходимости и **добавляет** поступление на `fact_amount`. |

## Порядок применения миграций

Миграция `migrations/014_payment_transactions.sql` нужна после `005` (счета). От `011` (журнал), `012` (переводы), `013` (округление) и `015` (Telegram) она **не зависит** — их можно применять в любом порядке.

Рекомендуемый порядок, если ещё ничего не применено: `011 → 012 → 013 → 015 → 014`.

- `013` лучше применить до `014`: поступления хранятся с точностью до цента, и без `013` старые суммы вроде `537.6344086` перенесутся как `537.63`.
- `014` переносит уже внесённые оплаты: одна строка `monthly_payments` с `fact_amount > 0` → одно поступление с теми же суммой, валютой, курсом, датой, счётом и комментарием (`created_by = 'backfill-014'`). Сам график при переносе не меняется. Повторный запуск ничего не дублирует.
- Всё выполняется в одной транзакции: при ошибке база не меняется.

Применение: Supabase → SQL Editor → вставить содержимое файла → Run.

Откат описан в конце файла миграции (раздел ROLLBACK). После отката приложение само вернётся к старому режиму, но отдельные поступления будут потеряны (останутся итоги месяцев).

## Как заново внести графики после очистки данных

1. Проверьте у каждого участника **дату начала**, **тариф** (если индивидуальный) и у программы **длительность** в месяцах — по ним строится график.
2. Участники → кнопка **«Сформировать графики»** вверху страницы. Приложение посчитает, сколько месяцев не хватает у активных участников, и покажет подтверждение: «Будет создано N строк графика для M участников». Уже существующие месяцы не меняются. Участники без даты начала, длительности программы или тарифа пропускаются (их количество будет в подтверждении).
3. Для одного участника: карточка участника → **«Сформировать график»** над таблицей месяцев.
4. Если план какого-то месяца отличается (скидка, рассрочка), нажмите на сумму в колонке «План» в карточке участника, введите новую и нажмите Enter. Можно задать план и для месяца, которого ещё нет в графике, — он будет создан.
5. Оплаты вносите через «Новое поступление» или кнопку «+» у месяца в карточке участника. С миграцией 014 оплату можно вносить частями.

Для разработчиков: то же через API.

```http
GET  /api/payments/schedule                        # предпросмотр для всех активных, ничего не пишет
GET  /api/payments/schedule?participant_ids=a,b    # предпросмотр для выбранных
POST /api/payments/schedule
{ "participant_ids": ["…"], "from_month": 9, "from_year": 2025, "months": 12, "plan_amount": 1000, "overwrite_plan": false }
```

Все поля, кроме `participant_ids`, необязательны: по умолчанию начало — месяц `start_date` участника, длительность — `duration_months` программы, план — тариф участника или цена программы. Ответ: `{ created, skipped, updated, participants: [...] }`.

Другие эндпоинты:

- `GET /api/payments/ledger` → `{ enabled }` — включены ли частичные оплаты;
- `GET /api/payments/transactions?participant_id=&monthly_payment_id=&account_id=&from=&to=` — поступления с именем участника, программой и счётом;
- `POST /api/payments/transactions` `{ participant_id, month_number, year, amount, currency, exchange_rate, paid_date, account_id, notes }` — добавить поступление (месяц создаётся с планом по тарифу, если его нет; существующий план не меняется);
- `DELETE /api/payments/transactions?id=` — удалить поступление;
- `PUT /api/monthly-payments` `{ id, plan_amount }` — изменить план месяца.

Все изменения пишутся в журнал. Удалённое поступление можно восстановить из корзины (если его месяц существует).

## Как проверить

После применения миграции 014 в Supabase:

```sql
-- поступлений столько же, сколько месяцев с оплатой
SELECT count(*) FROM payment_transactions;
SELECT count(*) FROM monthly_payments WHERE fact_amount > 0;

-- итог месяца совпадает с суммой поступлений (0 строк; без 013 возможны доли цента)
SELECT mp.id, mp.fact_amount, sum(t.amount_usd)
  FROM monthly_payments mp JOIN payment_transactions t ON t.monthly_payment_id = mp.id
 GROUP BY mp.id HAVING round(mp.fact_amount::numeric, 2) <> sum(t.amount_usd);
```

В приложении (через минуту после миграции):

1. Доходы и расходы → Поступления: подписи «за сен 2026» под участниками — значит, список идёт по поступлениям. Итог «Поступления» совпадает с прежним (до центов).
2. Остатки счетов и ОПиУ за прошлые месяцы совпадают с тем, что было до миграции (до центов, если `013` не применялась).
3. Внесите участнику $300 за текущий месяц, затем ещё $200: в форме второй раз видно «Оплачено $300 из $1 000 · осталось $700», после сохранения месяц «Частично», в карточке участника под месяцем две строки.
4. Удалите одно поступление в карточке участника: «Оплачено» месяца уменьшится.

## Для разработчиков

- `lib/payment-schedule.ts` — чистые функции: статус в центах, остаток, месяцы графика, полный график участника (`buildSchedule`, правила просрочки те же, что у `overdueMonths`).
- `lib/payments-ledger.ts` — проверка наличия таблицы (кэш: «есть» — навсегда, «нет» — 60 секунд) и чтение поступлений.
- Предпросмотр режима поступлений без миграции (только в `next dev`, в продакшене выключен): cookie `pp-ledger-mock=1` (часть оплат разбита на две для наглядности) или `pp-ledger-mock=flat` (одно поступление на месяц — для сверки отчётов), либо `PAYMENTS_LEDGER_MOCK=1` в окружении. Поступления в этом режиме собираются из `monthly_payments` и доступны только для чтения: запись поступлений отклоняется.
- Тесты: `tests/payments-ledger.test.ts`.
